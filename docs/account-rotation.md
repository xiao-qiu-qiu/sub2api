# 实验性账号轮休

在「系统设置 → 网关 → 调度 → 实验性账号轮休」开启。默认关闭；开启后的默认排空策略为激进模式，工作窗口 300 分钟，静置 10–30 分钟，错峰弹性 ±10%。这是一项调度实验，效果需结合账号质量检测观察。

账号真正接到请求、并发从零变为正数时开始计时。工作期间连续超过 5 分钟没有请求，下次接单重新开始一个完整工作窗口。这里算经过的时间，不累加每个请求的执行时长。

到达计划时间后，账号进入排空：

- **激进模式**：所有后续请求重新选号，包括已有黏性会话的新请求；当前正在执行的请求继续完成。
- **温和模式**：只允许已有黏性会话续跑，新会话换号；可能因持续续请求而延后静置。

排空期间，普通请求与 Live 租约的总并发归零后，立即开始随机静置。静置期间旧黏性也不能进入，到期后重新接单。人工停用、质量运维停调、限流和分组规则继续生效；轮休不会修改账号的 `schedulable`。

账号列表会显示待接单、计时、低并发观察、排空、静置或逐步恢复状态，区分手动和提前静置，并显示倒计时、等待请求数量。悬停可查看计划排空或恢复时间。正在观察、排空、静置或逐步恢复的可见账号每 5 秒单独刷新状态，不依赖整表自动刷新；页面隐藏时暂停。

## 手动静置与提前静置

在账号行右侧「更多 → 手动静置」中填写时长并确认，默认 1 分钟，可设为整数 1–120 分钟。无需开启自动轮休。确认后立即拦住分配给该账号的新请求，包括黏性续请求；请求保持原连接、原账号等待，当前在途请求继续完成。**最后一条在途请求结束后才开始静置计时**，等待队列不算账号并发，也不会延长静置。

例如 12:00 确认静置 1 分钟，最后一条请求在 12:03 结束，则 12:04 开始放行。恢复时先放行一条，之后每隔随机 **0.5–2 秒**再放行一条，直到积压队列清空；无需等待上一条执行结束，账号并发上限仍然有效。恢复期间的新请求也按同一节奏进入，客户端断开会退出等待。客户端或反向代理的超时仍然有效，静置期间不返回模型首字。

「实验性账号轮休」中的恢复间隔下限、上限按秒填写，支持小数；两者相同即为固定间隔。无需开启自动轮休也能调整，手动静置、提前静置和手动结束静置后的积压请求均适用。间隔按账号在 Redis 中统一控制，多实例共享；队列清空且最后一个间隔结束后恢复正常接单。没有积压请求时正常恢复。

同一菜单可「结束手动静置」。提前结束保留原工作计时，不将未完成的静置算成新周期。已经处于自动排空或静置的账号不能用手动操作缩短现有休息。

在轮休设置中开启「低并发提前静置」，系统从该账号**计划排空时刻前 20 分钟**开始观察。普通请求与 Live 的总并发低于 2（0 或 1）时，采用相同的等待策略，最后一条在途请求结束后静置 2 分钟。完成静置后，下次真实接单启动新工作窗口；未触发则继续按原到期策略轮休。此开关默认关闭，随自动轮休总开关生效。

提前观察跟随错峰规划后的排空时刻。例如计划在 5 小时 10 分钟排空，则从 4 小时 50 分钟开始观察。准入、释放和续租都会推进状态；持续运行的普通请求约每 20 秒续租一次。

## 错峰方式

同平台、同分组归属的账号共享一个规划池。每次启动工作窗口时，在设定时长的弹性范围内评估候选时刻，依次优先选择预计静置重叠峰值较小、重叠总时长较短、接近目标时长的位置。静置时长在该轮规划时抽取，排空完成后执行。

默认 300 分钟、±10%，意味着计划排空可落在接单后的 270–330 分钟。设为 0% 则严格按设定工作时长排空。算法使用有界扫描，不保证全局最优；长请求、自然空闲、不同模型的账号资格和账号增减都会影响实际同时可用数量。账号不足时仍会完成静置，由现有可用账号或故障转移路径承接；没有合格账号时返回暂时不可用。

## 配置与运行

管理设置的 `account_rotation_settings` 接受以下字段：

| 字段 | 默认值 | 范围 |
| --- | --- | --- |
| `enabled` | `false` | 开关 |
| `mode` | `aggressive` | `aggressive` / `sticky` |
| `work_minutes` | `300` | 整数 1–1440 |
| `rest_min_minutes` | `10` | 整数 1–120 |
| `rest_max_minutes` | `30` | 不小于下限，最大 120 |
| `stagger_percent` | `10` | 整数 0–30 |
| `early_rest_enabled` | `false` | 提前静置开关 |
| `recovery_min_interval_ms` | `500` | 整数 1–60000，界面按秒填写 |
| `recovery_max_interval_ms` | `2000` | 不小于下限，最大 60000 |

`revision` 由服务端维护。修改策略会重置普通旧周期；已经开始的手动或提前静置会完成后再按新配置运行。逐步恢复中的已确定放行时刻保留，后续间隔采用新配置。旧配置缺少恢复间隔字段时使用默认值。其他服务实例最多约 30 秒刷新配置。Redis 保存状态并提供统一时钟，检查、占槽和最后一个请求释放都采用原子操作。长请求持续续租并发槽，避免仍在生成时被判定为空闲；自动轮休关闭时仍跟踪真实并发，以支持随时手动静置。Redis 状态丢失后，计时会重新建立。

手动操作接口：`POST /api/v1/admin/accounts/:id/rotation/rest`，请求体为 `{"minutes":1}`；`DELETE` 同一路径结束手动静置，`GET` 查询当前状态。返回 `data.account_rotation`。重复开始正在执行的手动静置不会延长倒计时。

适用于网关调度的账号与上游，HTTP、WebSocket 每轮、Live 和网关辅助请求均参与准入；未经过网关调度的管理员主动测试、后台账号维护任务独立运行。手动及提前静置会等待同账号恢复；普通到期轮休要求换号时，已建立且不能迁移上游会话的 WebSocket 会在下一轮返回关闭码 `1013`，客户端需携带完整上下文重连。绑定账号的远程缓存资源也不能透明转移，普通到期轮休时返回暂时不可用。

当前使用 Redis 并发权威；配置了 regional SQL 并发的实例会拒绝启用自动轮休及手动静置。
