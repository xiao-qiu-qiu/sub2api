# BPS 冷却期间的请求等待

已绑定账号收到 BPS 上游 429 后，新来的会话请求优先留在原连接上等待。冷却结束后重新检查账号状态并继续调度；单个请求从首次等待起累计达到 30 秒，才允许按原有策略换号。

- 等待期间保留原黏性绑定，不占用用户、API Key 或账号的生成并发名额；恢复后重新申请名额。
- 重复限流和冷却延期共用这 30 秒，不会重新开始计时。不同请求独立计时，WebSocket 的每个新回合使用新预算。
- 客户端取消会立即停止该请求的等待；其他请求和账号冷却不受影响。流式 HTTP 等待沿用现有心跳。
- 尚未输出内容且可安全重试的 BPS 429，也先等待；已经输出内容或产生用量的请求遵循原有不可重放规则。
- 达到等待上限后按正常调度规则选择可用账号，可能更新黏性绑定；硬绑定续接仍遵循原有跨账号限制。

该等待针对 BPS 429 的临时冷却。原生 Codex 路由、模型权限拒绝、人工停用和分组权限继续执行各自规则。等待请求保留在当前进程和客户端连接中，不写入持久任务队列。

OAuth 账号的 5 小时或 7 天额度已用 100%，且快照有尚未到达的重置时间时，会直接退出业务调度；无需配置提前暂停阈值，关闭提前暂停也不会放行已耗尽的窗口。新选号、粘性会话和发送前准入均检查额度，窗口重置后恢复评估。

BPS 明确返回 `usage_limit_reached` 或 `insufficient_quota`，并且最新可信额度快照确认耗尽时，按该窗口的重置时间冷却，跳过这段短时等待。普通 TPM 限流继续采用短冷却。已接受的生成仍遵循原有不可重放规则；管理员手动测试保留直通行为。
